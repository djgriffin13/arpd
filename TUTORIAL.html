Start

In this tutorial you use ARPD to have AI agents build a small Spades card game with a window: you plus three computer players, one of them your partner. The game also records every bid and card played in a CSV file you can open in a spreadsheet. You act as the researcher in charge (ARPD calls you the PI): you describe what you want, settle the decisions that are yours, approve a plan, and the agents build and test it.

The goal is a first demonstration: a game window you can point and click at. When ARPD reaches that point it stops and asks you to try it. That is a good place to pause and review.

This is a deliberately simple example. As you go, think about a question of your own and the tool it would need; Your own project at the end gives the same steps at a high level.

Time: about 1 hour. Agent use: about $7.50 in credits.

You can stop and restart at any point. ARPD saves everything in the project's files, not in the conversation. To pick up again, open Claude Code in the same folder and type /arpd-checkin.

There is also an HTML version of this tutorial (TUTORIAL.html) with search and one stage per page: download it and open it in your browser.

Install and start

These are the README's Start here steps.

1. What you need

  • A Claude Pro, Max, Team or Enterprise plan, or a Claude Console (API) account. The free Claude plan does not include Claude Code.
  • Windows 10 or later, macOS 13 or later, or a recent Linux.
  • About 1 hour for the tutorial, much of it the agents working while you wait, and about $7.50 in agent credits.

2. Install Git

  • Windows: download and install Git for Windows from <https://git-scm.com/downloads/win> (the default options are fine). Claude Code also uses the Git Bash it includes.
  • macOS: open Terminal and run git --version. If Git is missing, macOS offers to install the command-line tools; accept.
  • Linux: install git with your package manager.

Then tell Git your name and email (any values you like; they label your own commits):

git config --global user.name "Your Name"
git config --global user.email "you@example.com"

3. Install Claude Code

Use Anthropic's installer. Commands from <https://code.claude.com/docs/en/setup>:

  • macOS / Linux (Terminal):

``bash curl -fsSL https://claude.ai/install.sh | bash ``

  • Windows (PowerShell):

``powershell irm https://claude.ai/install.ps1 | iex ``

Open a new terminal window and check that it worked:

claude --version

If claude is not found, see <https://code.claude.com/docs/en/troubleshoot-install>.

4. Check Python and its window toolkit

The tutorial builds a small windowed game in Python with Tkinter, which comes with most Python installations.

  • Windows (PowerShell): run py --version, then py -m tkinter.
  • macOS / Linux: run python3 --version, then python3 -m tkinter.

The second command should open a small test window; close it. If Python is missing, install it from <https://www.python.org/downloads/>. Some Linux and Homebrew Pythons ship without Tkinter; add it with your package manager (for example python3-tk on Ubuntu, python-tk on Homebrew).

Without Python (untested): you can still follow the tutorial, but in your first message to ARPD replace "Use Python with its built-in Tkinter" with a language you have (for example R). The game will then be built differently, and the run commands later in the tutorial will not apply. ARPD's own checks then run as read-throughs instead (arpd/docs/NO-PYTHON.md).

5. Get ARPD

Clone the repository into a new folder named spades-demo and go into it:

git clone https://github.com/djgriffin13/arpd.git spades-demo
cd spades-demo

If you have a ZIP download instead, unzip it, rename the folder spades-demo if you like, and open a terminal in that folder. ARPD works the same either way.

6. Start Claude Code

In that folder, run:

claude

The first time, Claude Code opens your browser to log in. When it asks whether you trust the files in this folder, answer Yes. You now see Claude Code's prompt.

7. Open the tutorial

Open TUTORIAL.md in your web browser and keep it open beside the terminal. Read it there, not in the folder: early in the tutorial, ARPD turns this folder into your project and moves its own files, including this README and the tutorial, into a backup folder beside it.

How to answer

ARPD is not scripted. It asks its questions in a different order each time, words them differently, and may skip some. Don't follow the cards below in order: find the card that matches the question you see, and use its reply. Use the search box (HTML version) or your browser's find (Ctrl+F / Cmd+F).

What you will see. When ARPD needs you, its message ends with a block between two lines, marked ❓, 🔘 or ✋, with the question and, often, lettered options. When it ends with ⏳ WORKING, nothing is needed from you: wait. A progress line such as SETUP ✅ Intake → 🔵 Objectives → ⚪ Constraints … shows where you are.

How each stage below is laid out: a short background, then the typical questions, in the usual order, then a list of other questions you may see, which you can filter. Click a question to see other ways ARPD may word it and a reply you can copy.

Quick ways to answer:

  • Suggested reply. Claude Code often shows a greyed-out suggested reply in the prompt. Press Tab or → to take it, then Enter. For this demo it is often good enough.
  • A letter. For a lettered choice, the letter of the option marked (recommended) is usually right for the demo.
  • "Do whatever you recommend." If you don't know, or it doesn't matter for the demo, say so. For a real project this is not good practice (the decisions are yours for a reason), but it is fine here.
  • "Yes." When ARPD asks whether it has understood you correctly ("Is that what you mean?"), reply yes unless it is clearly wrong. You are welcome to answer any question however you like.

Three answers commit you: adopting the project definition, approving the plan, and starting the build. For those, read what ARPD shows you and say yes only if it matches what you asked for; otherwise say what is wrong. They are what keep you in charge.

Permission prompts. Claude Code asks before it edits files or runs commands. For edits and commands inside your spades-demo folder, choose Yes (or the option that allows them for the session). Say No to anything outside the folder you did not expect, and ask ARPD why.

Why a card game?

The game is a toy, but it has the shape of a real research instrument:

  • Exact rules that the software must implement correctly, and that only you can settle when they are unclear.
  • Artificial agents (the computer players) whose behaviour you specify, so it can be checked.
  • A team task. Spades is a partnership game: partners commit to a joint goal (the team's bid) and must coordinate without talking, under incomplete information: a small version of the coordination problems studied in organizational research.
  • Behavioural data: every decision is recorded, with how long you took to make it.

From here, the step to interaction between several people is short: networked play so that four people play as two teams; human–AI teams in which the computer partner's strategy is the experimental condition; a chat channel between partners; or new measures in the play log. Each is another round of the same steps with ARPD.

Typical questions, in the usual order

The brief: paste this whole text as your first answer

Reply

I want a simple Spades card game with a window (GUI) that I can play on this computer: me plus
three computer players. The player opposite me is my partner. Use Python with its built-in Tkinter
and no other packages. Keep it simple: no networking, no card images (text like "Q♥" is fine), no
saving or resuming games, no clever AI. A later version could be networked; not now.

Rules: standard four-player partnership Spades.
- 52 cards, 13 each, aces high. The first dealer is random; then the deal passes clockwise.
- Bidding starts left of the dealer and goes clockwise, one round, no passing. Each player bids
  0-13; a bid of 0 is nil. No blind nil. A team's bid is the sum of the partners' bids.
- The player left of the dealer leads first. Players must follow suit if they can; otherwise they
  may play any card. The highest spade wins the trick, or else the highest card of the suit led.
  The winner leads next.
- Spades may not be led until a spade has been played on another suit, unless the leader holds only
  spades.
- A team that makes its bid scores 10 x bid, plus 1 per extra trick (a "bag"); a team that falls
  short scores -10 x bid. Nil scores +100 if that player takes no tricks, -100 if they take any; the
  partner's bid is scored on its own, and a nil bidder's tricks don't count toward it but always count
  as bags, whether or not the team makes its bid. Every 10 bags costs 100 points; extra bags carry
  over.
- The first team to 500 wins. If both reach 500 on the same hand, the higher score wins. If the
  scores are tied, play another hand.

Computer players use exactly these rules, nothing more. They choose only from the cards they may
legally play. Card order for "lowest" and "highest": non-spades by rank (on equal rank, clubs <
diamonds < hearts), then spades by rank. A card "would win" if it beats every card played to the
trick so far. "Above 10" means J, Q, K or A. The bid count adds up its three parts.
- Bid: count 1 per ace, 1 per king with at least one other card of its suit, and 1 per spade beyond
  the third. If the count is 0 and the hand has no spade above 10, bid nil; otherwise bid the count,
  at least 1.
- Lead: the highest card of its longest non-spade suit (on equal length: clubs, then diamonds, then
  hearts); if it may lead only spades, its lowest spade.
- Not leading: if its partner is winning the trick, play its lowest card; otherwise its lowest card
  that would win; if none would win, its lowest card.
- If it bid nil: lead its lowest card; otherwise play its highest card that would not win, or, if
  every card would win, its highest card. Its partner plays normally.

Aim for a first demonstration: as soon as there is a window I can click through, stop and ask me
to try it, before refining or polishing anything.

In the window: my hand as clickable cards, with only legal cards active; the four cards on the
table; each player's bid and tricks; both teams' scores and bags; computer plays shown with a short
pause; buttons to bid 0-13; a summary after each hand; a new-game button at the end.

Play log: record every bid and every card played, and save it as a CSV file in a "data" folder,
one file per game, named by the date and time the game started. Write the finished hands at the
end of each hand, so a game stopped part-way keeps them. One row per bid or card, with these columns:
- game_id: the same for every row of one game
- hand: 1, 2, 3, ...
- trick: 1-13 for cards; blank for bids
- seat: S, W, N or E (I am S, my partner N)
- player: human or computer
- team: NS or EW
- action: bid or play
- value: the bid (0-13), or the card as rank and suit letters, such as QH or 10S
- legal_options: how many legal choices that player had
- think_seconds: for my actions, seconds from when I could act to my click; blank for computers
- trick_winner: on the last card of each trick, the seat that won it; otherwise blank
- timestamp: date and time of the action
The log holds only my own play on this computer, with no names.

Tests: the rules, the scoring, each computer rule, the play log (a hand gives 4 bid rows and 52
card rows, with the columns above), and a game played by four computer players to the end, which
fails if no team has won within 200 hands. No test may open the window or wait for a click:
test the game logic without the window.

If ARPD asks later what you want, or whether there is existing work, reply: "The brief in my first message covers it; there is no existing work."

8 · Plan the build

Planning turns the adopted definition into a concrete plan. ARPD reviews where the project stands, asks what you want this piece of work to achieve, sizes it (usually two sprints here: the game logic with its tests, then the window), and writes a versioned plan under reports/planning/. You approve that exact version, then say whether to start now. Approving the plan and starting the build are the other two answers that commit you. Approval alone starts nothing. About 5 minutes. If ARPD offers to start planning at the end of setup, accept; otherwise type /arpd-plan.

For the demo, plan the whole first version at once and let the agents carry on between sprints without stopping. The aim is the first clickable demonstration.

9 · The build

The agents now write the game and its tests, and a separate reviewer agent checks the work. This is the longest part (about 20–40 minutes). You mostly wait.

What is normal:

  • Tool activity scrolling by, and test runs.
  • ⏳ WORKING or "Waiting for 1 background agent to finish": a reviewer is checking the work. Do nothing; ARPD continues when it finishes.
  • A question in the middle of the build about a rule detail. Answer it (see the cards below).
  • The context fills up. On a long build Claude Code may compact the conversation automatically, or ARPD may ask you to. Afterwards, type continue.

At any time you can type /arpd-checkin to see what is done, what is in progress, and what (if anything) needs you.

10 · Try the game

When the first clickable version exists, ARPD stops and asks you to try it. It also writes a short walkthrough checklist (reports/WALKTHROUGH-M1.md).

  1. Open a second terminal in the same folder and start the game with the command ARPD gives you (usually python -m spades, or py -m spades on Windows).
  2. Play one hand. A full game to 500 is optional; the tests already play whole games.
  3. Open the newest CSV file in the data folder in a spreadsheet. Each row is one bid or card, with your think time on your own rows. What could you study with it? What would you add?
  4. Tell ARPD what you saw, in plain words: either that it works, or what looks wrong. For example:
It works: I played a hand and the CSV opened with one row per bid and card.
My partner played a spade when it could have followed suit.

That is the normal loop: you report, the agents fix and test, and you check. "Built and reviewed" by the agents still leaves your own check: only you can say the first version is done.

Your own project

The same steps work for a tool of your own: an experiment platform, a simulation, a survey or measurement tool, a data pipeline, or an extension of this game.

  1. Start from a fresh copy. Clone ARPD into a new folder named for your project (README, Start here, step 5), open Claude Code there, and type /arpd-setup.
  2. Describe what you want in your own words: the question, the tool you think you need, who will use it, and what data it handles. A rough idea is fine; setup draws out the rest. Mention any existing notes, code or data, and say early if the tool will collect data from people.
  3. Choose ARPD's role. A builds what you specify. C also reviews how well the design fits your theory or research question. D helps you work out what to build and develop the science behind it with you.
  4. Work through the phases. Settle what is yours: the rules of the task, what each recorded value means, and what would convince you the tool works. On a real project, answer these yourself rather than delegating them.
  5. Read and adopt the Project Definition Report. Nothing is built before this.
  6. Plan a small first piece with /arpd-plan, aimed at a first demonstration you can try. Approve the exact version, then begin.
  7. Check in and review. /arpd-checkin shows where things stand. Try each demonstration yourself. /arpd-amend changes a ruling or the charter. Plan the next piece with /arpd-plan.

Start small. A first demonstration you can try within a session teaches you more than a long specification. For example, turn this game into a small experiment: give the computer partner two strategies, assign one per game as the condition, and compare the play logs.

Afterwards, look at: CLAUDE.md (the team charter the agents work under), DECISIONS.md (your rulings, word for word), REQUIREMENTS.md (each requirement and its evidence), reports/ (the setup record, the approved plan and the sprint close-outs) and arpd/docs/GUIDE.md (the full guide).
