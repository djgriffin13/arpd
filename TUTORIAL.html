Welcome

In this tutorial you use ARPD to have AI agents build a small Spades card game: a window in which you play with three computer players, one of them your partner. The game also saves every bid and card to a CSV file you can open in a spreadsheet.

You take the role ARPD calls the PI, the researcher in charge. You describe what you want, settle the questions that are yours to settle, and approve the plan; the agents write and test the code. The goal is a first demonstration, a game window you can click through. When the agents reach it, ARPD stops and asks you to try it.

The walkthrough takes about an hour and uses roughly $7.50 of agent credit. You can stop at any point: ARPD keeps its state in the project's files rather than in the conversation, so you can pick up again by opening Claude Code in the same folder and typing /arpd-checkin.

A note to new users. This walkthrough is designed so you can see ARPD work from start to finish with as little effort as possible, mostly by copying suggested replies. That is not how ARPD is meant to be used. On a real project, the value lies in working with it: reading what it proposes, questioning how it has interpreted you, and making the research decisions yourself. Accepting every recommendation unread is how agent-built research tools go wrong.

The example is deliberately simple. As you go, you might think about a tool your own research could use; Run ARPD on your own idea describes how to start one. If you're wondering why the example is a card game, see Why a card game? under Background. For the whole process on one page, see the diagram in About ARPD.

The tutorial is also available as a searchable web page: TUTORIAL.html. Next: Install and launch, which ends with setting Claude Code to Sonnet at low effort for this demonstration.

Install and launch

Follow Start here in the README to install Git, Claude Code and Python, and to clone ARPD into a folder named spades-demo. On the web page, the same steps follow here.

1. What you need

  • A Claude Pro, Max, Team or Enterprise plan, or a Claude Console (API) account. The free Claude plan does not include Claude Code.
  • Windows 10 or later, macOS 13 or later, or a recent Linux.
  • About 1 hour for the tutorial, much of it the agents working while you wait, and about $7.50 in agent credits.

2. Install Git

  • Windows: download and install Git for Windows from <https://git-scm.com/downloads/win> (the default options are fine). Claude Code also uses the Git Bash it includes.
  • macOS: open Terminal and run git --version. If Git is missing, macOS offers to install the command-line tools; accept.
  • Linux: install git with your package manager.

Then tell Git your name and email (any values you like; they label your own commits):

git config --global user.name "Your Name"
git config --global user.email "you@example.com"

3. Install Claude Code

Use Anthropic's installer. Commands from <https://code.claude.com/docs/en/setup>:

  • macOS / Linux (Terminal):

``bash curl -fsSL https://claude.ai/install.sh | bash ``

  • Windows (PowerShell):

``powershell irm https://claude.ai/install.ps1 | iex ``

Open a new terminal window and check that it worked:

claude --version

If claude is not found, see <https://code.claude.com/docs/en/troubleshoot-install>.

4. Check Python and its window toolkit

The tutorial builds a small windowed game in Python with Tkinter, which comes with most Python installations.

  • Windows (PowerShell): run py --version, then py -m tkinter.
  • macOS / Linux: run python3 --version, then python3 -m tkinter.

The second command should open a small test window; close it. If Python is missing, install it from <https://www.python.org/downloads/>. Some Linux and Homebrew Pythons ship without Tkinter; add it with your package manager (for example python3-tk on Ubuntu, python-tk on Homebrew).

Without Python (untested): you can still follow the tutorial, but in your first message to ARPD replace "Use Python with its built-in Tkinter" with a language you have (for example R). The game will then be built differently, and the run commands later in the tutorial will not apply. ARPD's own checks then run as read-throughs instead (arpd/docs/NO-PYTHON.md).

5. Get ARPD

Clone the repository into a new folder named spades-demo and go into it:

git clone https://github.com/djgriffin13/arpd.git spades-demo
cd spades-demo

If you have a ZIP download instead, unzip it, rename the folder spades-demo if you like, and open a terminal in that folder. ARPD works the same either way.

6. Start Claude Code

In that folder, run:

claude

The first time, Claude Code opens your browser to log in. When it asks whether you trust the files in this folder, answer Yes. You now see Claude Code's prompt.

7. Open the tutorial

Open TUTORIAL.md in your web browser and keep it open beside the terminal. Read it there, not in the folder: early in the tutorial, ARPD turns this folder into your project and moves its own files, including this README and the tutorial, into a backup folder beside it.

Set the model for this tutorial

For this tutorial, run Claude Code with Sonnet at low effort. It is fast, inexpensive and enough for a small demonstration. This setting is for the tutorial only; for your own projects, see Choosing a model and effort.

In your spades-demo folder, start Claude Code this way instead of plain claude:

claude --model sonnet --effort low

If Claude Code is already running, type /model to pick Sonnet and /effort to pick low instead.

Keep this tutorial open in your browser rather than in the folder. Early in setup, ARPD turns the folder into your project and moves its own files, including this one, into a backup folder.

How to answer

ARPD is not scripted. It phrases its questions differently from run to run, sometimes in a different order, and may skip some. Rather than working through the cards below in sequence, find the card that matches the question in front of you and use its reply. The search box on the web page, or your browser's find (Ctrl+F or Cmd+F), makes this quick.

When ARPD needs something from you, its message ends with a short block between two horizontal lines, marked ❓, 🔘 or ✋, containing the question and often lettered options. If it ends with ⏳ WORKING instead, nothing is needed and you can wait. A progress line such as SETUP ✅ Intake → 🔵 Objectives → ⚪ Constraints … shows where you are.

Each stage below begins with a short explanation, followed by the questions ARPD usually asks, in their usual order, and then other questions you may see. Click a question to see other ways ARPD phrases it, a reply you can copy, and an example from one of our runs.

For this demo, a few shortcuts work well:

  • Claude Code often shows a greyed-out suggested reply. Press Tab or → to accept it, then Enter.
  • For a lettered choice, the option marked (recommended) usually suits the demo.
  • If you don't know, or it doesn't matter here, reply "Do whatever you recommend."
  • When ARPD checks that it has understood you ("Is that what you mean?"), reply "Yes" unless it is clearly wrong.

You can always answer in your own words instead. On your own projects, treat ARPD as a collaborator rather than an autopilot: read its summaries, push back when a recommendation doesn't fit your research, and keep the decisions about rules, measures and data for yourself. ARPD is designed to stop and ask about exactly those, which only helps if you answer them.

Three steps need your explicit approval: adopting the project blueprint, approving the plan, and starting the build. At each one, read what ARPD shows you, and agree only if it matches what you asked for; otherwise, tell it what is wrong.

Claude Code also asks permission before it edits files or runs commands. Inside your spades-demo folder, choose Yes, or the option that allows them for the rest of the session. If it asks about anything outside that folder that you didn't expect, choose No and ask ARPD why.

Setup interview

Setup is an interview in five phases: Intake, Objectives, Constraints, Design and Development. Each ends with a summary for you to confirm. Then ARPD writes the project blueprint, one document with everything you agreed, for you to adopt. Nothing gets built during setup, which takes 20 to 30 minutes.

A progress line at the end of ARPD's messages shows which phase you're in, for example:

SETUP ✅ Intake → ✅ Objectives → 🔵 Constraints → ⚪ Design → ⚪ Development → ⚪ Blueprint

The next six pages follow the phases in order:

  1. Intake: who you are, what you want to build, and where it will live.
  2. Objectives: what the game is for and what would convince you it works.
  3. Constraints: the limits the work must respect.
  4. Design: how it's built and what its data mean.
  5. Development: how the agents will work.
  6. Blueprint: the document you adopt, and what happens next.

Setup 1 · Intake

You'll see: SETUP 🔵 Intake → ⚪ Objectives → ⚪ Constraints → ⚪ Design → ⚪ Development → ⚪ Blueprint

To start, type:

/arpd-setup

ARPD looks over the folder and asks what you'd like to accomplish. Here is what that looked like in one of our runs; every ARPD question ends with a block like this:

Paste this whole brief as your answer:

Typical questions, in the usual order

The brief: paste all of this as your first answer

Reply

I want a simple Spades card game with a window (GUI) that I can play on this computer: me plus
three computer players. The player opposite me is my partner. Use Python with its built-in Tkinter
and no other packages. Keep it simple: no networking, no card images (text like "Q♥" is fine), no
saving or resuming games, no clever AI. A later version could be networked; not now.

Rules: standard four-player partnership Spades.
- 52 cards, 13 each, aces high. The first dealer is random; then the deal passes clockwise.
- Bidding starts left of the dealer and goes clockwise, one round, no passing. Each player bids
  0-13; a bid of 0 is nil. No blind nil. A team's bid is the sum of the partners' bids.
- The player left of the dealer leads first. Players must follow suit if they can; otherwise they
  may play any card. The highest spade wins the trick, or else the highest card of the suit led.
  The winner leads next.
- Spades may not be led until a spade has been played on another suit, unless the leader holds only
  spades.
- A team that makes its bid scores 10 x bid, plus 1 per extra trick (a "bag"); a team that falls
  short scores -10 x bid. Nil scores +100 if that player takes no tricks, -100 if they take any; the
  partner's bid is scored on its own, and a nil bidder's tricks don't count toward it but always count
  as bags, whether or not the team makes its bid. Every 10 bags costs 100 points; extra bags carry
  over.
- The first team to 500 wins. If both reach 500 on the same hand, the higher score wins. If the
  scores are tied, play another hand.

Computer players use exactly these rules, nothing more. They choose only from the cards they may
legally play. Card order for "lowest" and "highest": non-spades by rank (on equal rank, clubs <
diamonds < hearts), then spades by rank. A card "would win" if it beats every card played to the
trick so far. "Above 10" means J, Q, K or A. The bid count adds up its three parts.
- Bid: count 1 per ace, 1 per king with at least one other card of its suit, and 1 per spade beyond
  the third. If the count is 0 and the hand has no spade above 10, bid nil; otherwise bid the count,
  at least 1.
- Lead: the highest card of its longest non-spade suit (on equal length: clubs, then diamonds, then
  hearts); if it may lead only spades, its lowest spade.
- Not leading: if its partner is winning the trick, play its lowest card; otherwise its lowest card
  that would win; if none would win, its lowest card.
- If it bid nil: lead its lowest card; otherwise play its highest card that would not win, or, if
  every card would win, its highest card. Its partner plays normally.

Aim for a first demonstration: as soon as there is a window I can click through, stop and ask me
to try it, before refining or polishing anything.

In the window: my hand as clickable cards, with only legal cards active; the four cards on the
table; each player's bid and tricks; both teams' scores and bags; computer plays shown with a short
pause; buttons to bid 0-13; a summary after each hand; a new-game button at the end.

Play log: record every bid and every card played, and save it as a CSV file in a "data" folder,
one file per game, named by the date and time the game started. Write the finished hands at the
end of each hand, so a game stopped part-way keeps them. One row per bid or card, with these columns:
- game_id: the same for every row of one game
- hand: 1, 2, 3, ...
- trick: 1-13 for cards; blank for bids
- seat: S, W, N or E (I am S, my partner N)
- player: human or computer
- team: NS or EW
- action: bid or play
- value: the bid (0-13), or the card as rank and suit letters, such as QH or 10S
- legal_options: how many legal choices that player had
- think_seconds: for my actions, seconds from when I could act to my click; blank for computers
- trick_winner: on the last card of each trick, the seat that won it; otherwise blank
- timestamp: date and time of the action
The log holds only my own play on this computer, with no names.

Details, so you don't need to ask:
- Seats go S, W, N, E clockwise; "left of the dealer" is the next seat clockwise.
- Every bag scores 1 point, including a nil bidder's tricks. Every full 10 bags costs 100, even
  several times in one hand.
- A spade led by a player who holds only spades breaks spades.
- Computer plays pause about 1 second (no pause in tests). With only one legal card, still wait for
  my click.
- Play log: game_id and the file name use the game's start time (data/spades-YYYYMMDD-HHMMSS.csv);
  timestamps are this computer's local time to the second; legal_options on a bid row is 14. A game
  stopped part-way just ends after its last finished hand. Keep the data folder out of git.
- If the all-computer test can't finish within 200 hands under these rules, tell me; don't change a
  rule.

Tests: the rules, the scoring, each computer rule, the play log (a hand gives 4 bid rows and 52
card rows, with the columns above), and a game played by four computer players to the end, which
fails if no team has won within 200 hands. No test may open the window or wait for a click:
test the game logic without the window.

If ARPD later asks again what you want, or about existing work, reply: "My first message covers it; there is no existing work."

Setup 6 · Blueprint

You'll see: SETUP ✅ Intake → ✅ Objectives → ✅ Constraints → ✅ Design → ✅ Development → 🔵 Blueprint

ARPD now writes the project blueprint (reports/setup/PROJECT-BLUEPRINT.md). It's one document with everything you agreed: the requirements and how each will be checked, the design, how the agents will work, and anything still open. ARPD checks it, summarizes it, and asks you to adopt it.

Adopting the blueprint is the first of your three approvals, so look it over first. Until you adopt it, everything from the interview is only notes and proposals. Once you do, ARPD writes the project's governing documents from it: the team charter CLAUDE.md, REQUIREMENTS.md, DECISIONS.md and others. About 5 minutes, mostly ARPD writing.

Worth noticing: open reports/setup/PROJECT-BLUEPRINT.md in any text editor. Your game rules and the computer players' rules should be recorded as yours, with nothing added that you didn't ask for.

Typical questions, in the usual order

Build the game

With the blueprint adopted, ARPD turns it into working software in three steps, each on its own page:

  1. Plan. You give the goal for this piece of work, ARPD drafts a versioned plan, and you approve it and say when to start. About 5 minutes.
  2. Build. The agents write the game and its tests, and a separate reviewer agent checks their work. You mostly wait; ARPD stops only for decisions that are yours. In our runs, 10 to 30 minutes.
  3. Try the game. At the first clickable version ARPD stops and asks you to try it. You play a hand and say what works and what doesn't.

Try the game

When a first clickable version exists, ARPD stops and asks you to try it. Expect it to be partial: in our runs the scores, the hand summary or the play log sometimes came later, in the next sprint. That's the point of stopping early: you see something real before the agents build the rest.

  2. Play a hand. Bid, then click your cards; only the cards you can legally play are active.
  3. If the play log exists yet, open the newest CSV file in the data folder in a spreadsheet. Each row is a bid or a card, with your think time on your own rows. What could you study with it, and what would you add?
  4. Tell ARPD what you saw, in your own words. For example:
It works: I played a hand and the CSV opened with one row per bid and card.
My partner played a spade when it could have followed suit.

That's the normal loop: you report, the agents fix and test, you check again. The agents' tests and reviews don't replace your own check; only you can say the first version is right.

Find a new direction

Once the game works, look at it as a research tool and ask what you could learn with it. A few directions it could take:

  • An experimental condition. Give the computer partner two strategies, assign one per game, and compare the play logs.
  • People playing together. Networked play, so four people play as two teams.
  • Communication. A chat channel between partners, logged alongside the play.
  • New measures. Hesitation before a bid, how often a partner's lead is followed, or how bids change after a failed contract.
  • A different kind of partner, such as a computer partner driven by a language model.

For each, ask the questions setup asked you: what is it for, what would convince you it works, and what does each new piece of data mean? Those answers are yours to give, and they are what ARPD will ask about.

Plan it and run it

Each new direction is another round of the same loop:

  1. Plan it. Type /arpd-plan and describe the goal in a sentence or two (an example follows).
  2. Approve and start. ARPD reviews where the project stands, sizes the work, drafts a plan, and asks you to approve that version and say when to start.
  3. Let the agents build it, as in the Build stage. They stop for any decision that's yours.
  4. Try it, and tell ARPD what you see.

For example, after typing /arpd-plan:

Run ARPD on your own idea

The same steps work for a tool of your own: an experiment platform, a simulation, a survey or measurement tool, or a data pipeline.

This time, take your time. In the tutorial you could accept ARPD's suggestions with little thought. On your own project, the interview is where the research gets defined: what the tool measures, what its data mean, and what would convince you it works. Read each summary and the blueprint carefully, question readings that don't match what you meant, and audit your own answers before you approve anything. The agents build exactly what you agree to.
  1. Start from a fresh copy. Clone ARPD into a new folder named for your project (README, Start here, step 5), open Claude Code there, and type /arpd-setup.
  2. Describe what you want in your own words: the question, the tool you think you need, who will use it, and what data it handles. A rough idea is enough; setup draws out the rest. Mention any notes, code or data you already have, and say early if the tool will collect data from people.
  3. Choose ARPD's role. A builds what you specify. C also checks how well the design fits your theory or research question. D helps you work out what to build and develops the science behind it with you.
  4. Work through the phases and settle what's yours: the rules of the task, what each recorded value means, and what would convince you the tool works. On a real project, answer these yourself.
  5. Read the project blueprint and adopt it. Nothing is built before that.
  6. Plan a small first piece with /arpd-plan, aiming for a first demonstration you can try.
  7. Check in, try each demonstration yourself, and plan the next piece.

A first demonstration you can try within a session teaches you more than a long specification, so start small.

Files worth a look in any ARPD project: CLAUDE.md (the team charter the agents work under), DECISIONS.md (your rulings, word for word), REQUIREMENTS.md (each requirement and its evidence), reports/ (the blueprint, the approved plans and the sprint records) and arpd/docs/GUIDE.md (the full guide).

Updating the process

The way the agents work is set during setup, but none of it is fixed. You can change it whenever the project needs it, in plain words, with /arpd-amend. ARPD records each change as a ruling in your words and updates the governing documents.

How closely you review. Ask for more or less oversight, for example:

From now on, I want to review each sprint's full record before the next one starts.

How far the agents go on their own. Widen or narrow what they may decide without you, or how they move from one sprint to the next:

The agents may choose test designs and file layout on their own, but must ask me before changing
anything in the play log.

The rules of the project. Change a requirement, a game rule, a milestone, or the team charter itself. A change to what the data mean is always yours to make, and ARPD will ask you to confirm it.

When you check in. /arpd-checkin works at any time. You can also ask for a check-in at every sprint boundary, or only when something needs you.

Keeping ARPD itself up to date. When a newer version of ARPD is released, clone it into a separate folder and run, from your project folder:

python arpd/tools/install.py update . --kit <path to the new ARPD folder>

This refreshes ARPD's own files and skills; it never changes your governing documents, code or data. (Without Python, use sh arpd/tools/install.sh update . --kit <path> instead.)

Why a card game?

The game is stylized, but games are an established way to study coordination and teamwork under controlled conditions. A recent review catalogued 103 testbeds, many of them games, used across 235 empirical studies of human–agent teams (Chung et al., 2026). Organizational researchers have long used simple laboratory tasks the same way: Weber and Camerer (2003) studied culture clash with small laboratory "firms" that built up their own way of working on a shared task and were then merged.

Card games in particular have served as research environments. Spades itself has been used to build computer players that imitate how people play (Baier et al., 2019). The cooperative card game Hanabi became a standard test of teamwork under hidden information (Bard et al., 2020), and in a study of human–AI teams playing it, people preferred a rule-based computer partner to a learned one even though their scores did not differ (Siu et al., 2021). In Codenames, an AI assistant helped players' individual thinking but got in the way of the team building a shared understanding (Sidji et al., 2024). Spades is not Hanabi: its partnerships compete against each other rather than all playing together. But it shares the features that matter here:

  • Exact rules the software must follow, which only you can settle when they're unclear.
  • Artificial agents, the computer players, whose behaviour you specify, so it can be checked.
  • A team task. Partners commit to a joint goal, the team's bid, and must coordinate without talking, each seeing only their own cards.
  • Behavioural data: every decision is recorded, along with how long you took to make it.

From here it's a short step to studying people together: networked play with four people in two teams, human–AI teams where the computer partner's strategy is the experimental condition, a chat channel between partners, or new measures in the play log. Each would be another round of the same steps with ARPD. Building this game shows the process working on one bounded project; it isn't evidence that ARPD suits every research tool.

About ARPD

ARPD stands for Agentic Research Paradigm Development. It is a framework and toolkit for researchers who want AI coding agents to build the research tools their questions need, while the researcher keeps authority over the science.

Why it exists

The questions researchers can ask are bounded by the tools they have to study them. Methods shape theory (Gigerenzer, 1991; Greenwald, 2012), and new research paradigms open questions that older ones could not reach. But building, validating and maintaining a new paradigm (an experiment platform, a measurement system, a computational model) is slow, costly and risky, and the cost usually falls on individual researchers. In March's (1991) terms, building a new paradigm is exploration, with uncertain and distant returns, while using an established one is exploitation, with predictable and immediate ones. So researchers often stay with tools whose limits they know well.

AI coding agents can lower the cost of that exploration. A researcher can now direct agents to build and revise an instrument they could not build alone or afford to commission. Left unguided, though, agents tend to produce work that is incomplete or inconsistent, or that passes its own checks while measuring the wrong thing, and the researchers who most need the help are the least able to spot it.

How it works

ARPD treats the researcher as the leader of a small team of agents, and borrows from research on teams: team charters (Mathieu & Rapp, 2009), team processes (Marks et al., 2001) and team leadership (Morgeson et al., 2010). In practice that means:

  • A charter and governing documents that set out the goals, the design, who decides what, and how work is checked, adapted to each project during setup.
  • Decision authority by subject. Agents handle the engineering. The rules of the task, what the data mean, and the scope stay with the researcher, and ARPD stops to ask about them.
  • Approvals at the points that matter: the blueprint, each plan, and the start of the build.
  • Independent checking. A reviewer agent that did not write the code checks each change, tests run without anyone present, and each requirement is marked as implemented, verified or validated.
  • A record you can audit: your rulings in your own words, versioned plans, and sprint records.

Stuck or interrupted

If ARPD seems to have stopped, go down this list:

  1. Is something still running? Tool output, a spinner, ⏳ WORKING or "Waiting for … background agent" mean wait.
  2. Did it ask you something? Look for a ❓ 🔘 ✋ block at the end of its last message and find the matching card.
  3. It stopped mid-task without a question: type continue.
  4. Still stuck: type
Continue the current sprint under the approved plan.
  1. Not sure where things stand: type /arpd-checkin. It lists what's done, in progress and waiting, and gives you the exact next prompt.
  2. The session is gone (closed, crashed, or out of usage): start Claude Code again in the same folder (for this tutorial, claude --model sonnet --effort low), type /arpd-checkin, and follow its next step.

Installing and launching

  • claude isn't found. Open a new terminal window after installing; the installer only updates new ones. If it still isn't found, see Anthropic's installation troubleshooting.
  • Claude Code won't let you in. It needs a paid Claude plan (Pro, Max, Team or Enterprise) or a Claude Console account; the free plan doesn't include it.
  • Git complains about your name or email. Run the two git config commands in the README's Start here, step 2.
  • The Tkinter test window doesn't open. Your Python was installed without it. On Linux, install python3-tk; with Homebrew on a Mac, python-tk; elsewhere, reinstall Python from python.org.
  • You downloaded a ZIP instead of cloning. That's fine: unzip it, open a terminal in that folder, and carry on. ARPD handles both.
  • Your folder is in OneDrive, Dropbox or a path with spaces. Syncing can lock files while the agents work. If you see odd file errors, move the folder somewhere local, such as your Documents folder outside any synced area.

Prompts and blocked commands

  • Permission prompts. Claude Code asks before it edits files or runs commands. Inside your spades-demo folder, choose Yes, or the option that allows them for the rest of the session.
  • A request outside the folder. If it asks about files or folders you didn't expect, choose No and ask ARPD why.
  • A command is blocked by Claude Code's safety check. ARPD gives you a one-line command starting with !. Paste it at the prompt and press Enter; it runs in your terminal, under your control.
  • You want to stop something. Press Esc to interrupt, then tell ARPD what you want instead. Nothing it has already saved is lost.

Changing your mind

  • During the interview. Just say so, for example "Actually, I'd like the game to go to 300 points." ARPD updates its notes, and a phase summary can be corrected before you confirm it.
  • Before adopting the blueprint or approving a plan. Say what's wrong instead of approving. ARPD revises it and asks again.
  • After adoption. Use /arpd-amend and state the change, for example "From now on, a team loses 100 points for every 5 bags." ARPD records your words as a ruling and updates the documents.
  • During the build. Press Esc, then say what you want changed. For anything bigger than a fix, ARPD will suggest planning it as a new piece of work with /arpd-plan.

Problems with the game

  • The window doesn't open. Run the Tkinter check from the README, step 4. If that works, tell ARPD the exact error message.
  • Nothing happens for 10 minutes or more during the build. A test may have opened the game window and be waiting for a click. Close any game window, and if it's still stuck, press Esc and type:
A command seems to be hanging, possibly a test that opened the game window. Stop it and continue.
  • Card symbols show as boxes. Ask ARPD to show suits as letters (S, H, D, C) instead.
  • The game breaks a rule, or scores something wrong. Tell ARPD what you saw, as precisely as you can, for example "My partner played a spade when it could have followed suit." It will find the cause, add a test, and fix it.

Starting over

  • Undo the conversion. Setup moves ARPD's own files and the old git history into a backup folder beside your project (named spades-demo-pre-arpd-backup-…). Its RESTORE.md explains how to put everything back.
  • Start from scratch. Delete the spades-demo folder and its backup, then clone ARPD again (README, Start here, step 5). Nothing else on your computer is changed.
  • Keep your project but redo a stage. Type /arpd-checkin to see where things stand. To revisit a decision, use /arpd-amend; to redo a piece of work, plan it again with /arpd-plan.

Choosing a model and effort

Claude Code lets you choose the model and how much effort it puts into each step.

  • For your own projects, Sonnet or Opus at medium or high effort is usually a good choice. Opus and higher effort cost more, but they think more carefully, which matters when the agents are building a research instrument you will rely on.
  • For a demonstration like this tutorial, Sonnet at low effort works well and keeps it quick and inexpensive.

To set them when you start, for example:

claude --model sonnet --effort medium

In a session that's already running, type /model or /effort and pick from the list.

Usage limits and cost

  • What it costs. The whole tutorial used about $7.50 of agent credit in our runs with Sonnet at low effort. Larger models and higher effort cost more; see Choosing a model and effort.
  • Hitting a usage limit. Claude Code tells you when you reach one. Nothing is lost: wait for it to reset, then start Claude Code in the same folder and type /arpd-checkin.
  • Keeping agent use down. Say "keep agent use low" when ARPD asks about cost, so it chooses lighter ways of working. Clearing the conversation between setup and the build (/clear, then /arpd-checkin) also helps.

Other AI tools

ARPD is developed and tested with Claude Code, and this tutorial assumes it. Its instructions are plain text files, though, so other coding agents that can read files, edit them and run commands in a folder (for example OpenAI's Codex, Google's Gemini CLI, or an editor such as Cursor, with models such as GPT, Gemini or DeepSeek) should be able to follow them. We have not tested them.

What differs:

  • Starting setup. The /arpd-setup, /arpd-plan, /arpd-checkin and /arpd-amend commands are Claude Code skills. In another tool, ask the agent to read and follow the skill file instead:
Read .claude/skills/arpd-setup/SKILL.md and follow it exactly.
  • Instructions on start-up. Claude Code reads CLAUDE.md automatically. Many other tools read AGENTS.md, which ARPD also provides and which points to the same charter.
  • Event logging. ARPD's activity log uses Claude Code hooks, so it won't run elsewhere. Nothing else depends on it.
  • Approvals and permissions look different in each tool. The three approvals (the blueprint, the plan, the start of the build) still come from you, in your own words.

A chat window without access to your files, such as the ChatGPT or DeepSeek website, can't run ARPD: it needs an agent that works directly in the project folder.

No Python

ARPD's own small tools are written in Python, but ARPD works without it, with a few things lost:

  • Setup still prepares the folder, using a shell script instead (sh arpd/tools/install.sh). On Windows this needs Git Bash, which comes with Git for Windows.
  • The automatic checks are replaced by read-throughs: ARPD checks the blueprint and the governing documents by reading them, which is less thorough. It tells you when it does this.
  • There is no activity log. Everything else (the interview, the blueprint, planning, check-ins and amendments) works the same.

The game itself is a separate matter: this tutorial builds it in Python. Without Python, change one sentence of the brief, "Use Python with its built-in Tkinter", to a language you have, for example "Use R", and expect the run commands later on to differ. That route is untested. Details are in NO-PYTHON.md.
